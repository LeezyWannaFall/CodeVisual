# Инструкции для агента

## Назначение проекта

CodeVisual — локальный инструмент для знакомства с архитектурой одного Go-модуля.
Он строит карту пакетов и объявлений, находит chi-маршруты и SQL DDL,
показывает возможные цепочки вызовов. Интерфейс встроен в Go-бинарник.

Общайся с пользователем по-русски, если он не попросил иначе. Сохраняй английский
язык существующего интерфейса, имён в коде и комментариев к коду.

## Перед началом работы

1. Прочитай `README.md` и относящиеся к задаче части `docs/ARCHITECTURE.md`.
2. Проверь `git status --short`. Сохраняй пользовательские изменения.
3. Для задач развития сверься с `docs/ROADMAP.md` и `docs/TASKS.md`.
4. Прочитай реализацию и существующие тесты перед изменениями. Документация может
   отставать от кода; сообщай о существенных расхождениях.

Roadmap и список задач — контекст, а не разрешение выполнять весь план.
Работай в пределах текущего запроса пользователя. Не создавай коммиты, не публикуй
релизы и не отправляй изменения в удалённый репозиторий без поручения.

## Архитектурные ограничения

- Анализ не должен исполнять код проекта, обработчики или SQL-миграции.
- Сохраняй автономный режим: анализ не скачивает зависимости и Go toolchain,
  не изменяет `go.mod` и `go.sum` исследуемого проекта.
- Сервер слушает только loopback. Сохраняй проверки Host/Origin и ограничения
  чтения файлов внутри корня исследуемого модуля.
- Не представляй возможные вызовы как подтверждённые runtime-пути.
- Не расширяй анализ на тесты, вложенные модули и символьные ссылки без отдельного
  решения с обновлением документации и проверок.
- Сохраняй ограничение размера представлений и доступность остальных результатов
  через поиск, навигацию или пагинацию.
- Изменения формата API согласуй между Go-моделью, TypeScript-типами,
  контрактной фикстурой и тестами.

## Как вносить изменения

- Предпочитай небольшие изменения, решающие конкретную задачу.
- Не добавляй зависимости и широкие рефакторинги без необходимости для задачи.
- При исправлении ошибки анализатора сначала воспроизведи её на минимальном
  примере; добавь проверку ожидаемых узлов, связей или диагностики.
- Не маскируй неподдерживаемые конструкции ложными результатами. Если анализ
  неполный, используй существующую систему диагностик.
- Соблюдай стиль соседнего кода. Форматируй изменённые Go-файлы через `gofmt`.
- После изменения фронтенда пересобери встроенные ресурсы через `make frontend`.
  Включай обновлённый `internal/server/webdist` в результат изменений.
- Если меняется пользовательское поведение, обнови соответствующую документацию.

## Проверки

Требования: Go 1.26+, Node.js 22.16+, npm. Актуальные команды находятся в Makefile
и `web/package.json`.

```sh
go test ./...
cd web && npm test
cd web && npm run build
```

Команды с `cd web` выше выполняются независимо из корня проекта.
`make test` запускает Go- и фронтенд-тесты; `make build` собирает интерфейс и бинарник.
Для браузерных сценариев сначала выполни `make build`, затем из `web`:

```sh
npx playwright install chromium
npm run test:e2e
```

Выбирай проверки по изменению. Для чисто документальных правок достаточно
проверить ссылки, команды и diff. Ошибки окружения описывай отдельно от ошибок
проекта. Не заявляй об успешной проверке, которую не запускал.

## Завершение задачи

- Проверь diff и отсутствие случайных изменений или временных файлов.
- Сообщи, что изменилось, какие проверки выполнены и что осталось непроверенным.
- При работе над задачей из `docs/TASKS.md` обнови её статус по фактическому
  результату. Не отмечай задачу завершённой только по результатам чтения кода.
- Не записывай в документацию секреты, личные пути и временные логи окружения.
