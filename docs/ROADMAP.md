# План развития

## Направление

CodeVisual помогает познакомиться с Go/Python-проектом и его Docker-конфигурацией:
найти пакет, объявление и исходник, понять зависимости и возможные вызовы. Приоритеты:
точность результатов, простота локального запуска, удобство исследования.

Этот план задаёт последовательность, но не фиксирует сроки и не означает,
что все перечисленные возможности уже согласованы для реализации.

## Этап 1. Точность анализа

Статус: реализован и проверен локально. Результаты — в `TASKS.md`.

- Воспроизвести замечания по chi-роутерам из `TASKS.md` и исправить подтверждённые.
- Обеспечить доступ к маршрутам за пределами первой страницы API.
- Добавить минимальные примеры для ошибок и неподдерживаемых конструкций.
- Проверять правильность путей, middleware, целей вызовов и диагностик.

Критерий: подтверждённые дефекты покрыты проверками; неполные результаты
сопровождаются понятными ограничениями.

## Этап 2. Воспроизводимые проверки и выпуск

Статус: реализация и локальные проверки завершены. Первый запуск CI и
нативная проверка на macOS/Windows ожидаются после отправки изменений.

- Настроить CI для Go, TypeScript, Vitest, сборки и основных e2e-сценариев.
- Проверять соответствие встроенного интерфейса исходникам.
- Автоматизировать сборку релизов под Linux, macOS и Windows.
- Добавить версию бинарника и понятную диагностику Go toolchain.

Критерий: установка по README воспроизводится на поддерживаемых платформах;
релизы проходят единый набор проверок.

## Этап 3. Навигация и основной сценарий

Статус: реализован и проверен локально. URL, перезагрузка, новая вкладка,
Back/Forward и восстановление контекста покрыты браузерными сценариями.

- Упростить управление навигацией, историей и фильтрами в `App.tsx`.
- Добавить адресуемое состояние представления и поддержку истории браузера.
- Улучшить переходы «поиск → пакет → символ → исходник → вызовы».
- Объяснять пустые представления и скрытые результаты.

Критерий: пользователь находит обработчик, исследует связи и возвращается назад
без потери контекста; поведение проверяется браузерными сценариями.

## Расширение по запросу: Python и Docker/Compose

Статус: реализовано и проверено локально. Задачи CV-009–CV-011 в `TASKS.md`.

- Автоматическое определение Go, Python и смешанных проектов, включая workspace
  с независимыми дочерними Go-модулями.
- Python AST: модули, импорты, классы, функции, методы, исходники и возможные вызовы.
- Схема Compose-сервисов и Dockerfile-стадий, сетей, томов, зависимостей,
  объявленного COPY/ADD и монтирований со ссылками на локальный код.

Анализ статический: Python-код не импортируется, Docker не запускается.
Содержимое образа и результат RUN не исследуются. Ограничения перечислены в README.
Это отдельное расширение; измерения производительности этапа 4 ещё не выполнялись.

## Дальнейшие кандидаты

Порядок уточняется после обратной связи пользователей:

1. Входящие вызовы и поиск использований функции.
2. Переход к исходнику в редакторе.
3. Повторный анализ без перезапуска приложения.
4. Экспорт схем в SVG/PNG.
5. Поддержка следующего HTTP-фреймворка.
6. Сравнение архитектуры двух версий проекта.

Облако, аккаунты и LLM-функции пока вне ближайшего плана.

## Предложение следующей итерации (не реализовано)

1. **Входящие вызовы и использования.** Сначала обратный индекс существующих
   calls с фильтрами direct/possible/dynamic, затем отдельные ссылки на символы,
   включая чтения/записи. Критерий: переход к каждому месту использования
   и исходнику, пагинация и сохранение неизвестных целей.
2. **Основания связей.** Показывать вид анализа, исходную строку, разрешённую
   цель и причину неопределённости в инспекторе ребра. Критерий: пользователь
   может проверить связь по исходнику; гипотезы явно отличаются от фактов.
3. **Порты и готовность контейнеров.** Разделить published host ports и
   exposed container ports, сохранить protocol/host IP и исходное объявление.
   Затем добавить условия depends_on и healthcheck (команда, интервалы, retries,
   disable). Критерий: схема показывает декларации, без утверждения о реальной
   доступности или порядке запуска; неподдерживаемые значения диагностируются.
4. **Повторный анализ.** Явная кнопка с отменой, прогрессом и атомарной заменой
   snapshot. Сначала повторный полный анализ, затем оценка необходимости кеша.
   Критерий: неуспешная попытка сохраняет предыдущий результат; старые запросы
   и ссылки не смешиваются с новым analysisId, файловые границы сохраняются.
5. **Производительность.** До оптимизаций выбрать малый, средний и большой
   Go/Python/mixed репозитории; измерить анализ, peak RSS, размер snapshot,
   API/search и время раскладки/взаимодействия. Зафиксировать версии, оборудование,
   холодные/повторные прогоны и распределение результатов. По измерениям
   согласовать бюджеты и приоритеты оптимизаций.

Порядок: сначала базовые замеры, затем входящие связи и их объяснения,
контейнерные метаданные, повторный анализ и повторные замеры.
